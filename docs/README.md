## 1. 这个仓库是什么

一个**安卓设备轨迹采集与查询器**的实现史，外加一份**记忆层契约**。

它**不是**：
- 产品最终形态的承诺
- 一套必须遵守的架构
- MVP 的起点（MVP 由另一条线从头做，参考本仓库而不照抄）

设计上，本仓库曾与「聊天 app + agent 记忆」并列为两条线，后来**降级为高价值素材**：
上层 agent loop / 人格 / 交互更适合作为 MVP 闭环，本仓库专注采集、重建、检索。

## 2. 可直接采信的实测结论

这些是花了很多轮验证出来的，数字都有出处，**重做一遍成本很高**，建议直接采信。

### 采集层

| 结论 | 出处 |
|---|---|
| `AccessibilityNodeInfo` **没有** scrollX/scrollY 读取器（`javap` 确认，只有 `isScrollable()`） | 设计文档 §4.5 |
| `TYPE_VIEW_SCROLLED` 的 delta **值错**：bilibili 全 0；QQ 报 3 而实际位移 897px | 同上 |
| 位移可行来源：①同一节点 bbox.top 差（QQ 实测精确 897px）②OCR 行匹配（微信 80%）③像素对齐（29%，仅无文字场景） | §4.5 / §4.4.1 / §4.4.3 |
| **微信的 A11Y 树是空的**（1 个空节点），文本只能来自 OCR；微信位移只能走 OCR 行匹配 | §4.6 |
| 滚动长截图可拼：静态层分离后无重复（逐行 moved-vs-still 判定） | §4.4.2 |
| 结构 chrome 可用**无词表判据**识别：该文本出现在多少个不同对象里（>100 个对象的只有 42 条，占 14.4% 行） | §`质量基线` |
| 解析成本 95% 在 `getChild()`，且是**争用**不是算力：同一棵树滚动中 422ms、静止后 37ms | §4.7 |
| 主线程解析会阻塞事件处理；把解析移出事件路径后 581ms → 20ms | 提交 `b47a58d` |

## 4. 契约（唯一耦合点）

`memory.db` 这一份文件格式 + 三个工具面（`recall` / `readBlock` / `readFrame`）。

完整语义见 **`docs/INTERFACE.md`**，要点：

```
recall(...) → { answer, ids, coverage, freshness }
  · answer 空串 = "没找到"，不等于"没有发生"
  · freshness 必选：{ projectedUntil, lagMs, state }，滞后必须对调用方可见
readBlock(blockId) / readFrame(frameId) → 失败必须带 reason，不抛异常
```

`freshness` 的存在理由是一个真实故障：`object_messages` 落后 18 小时，
系统对一条确实存在的消息回答了"没看到"。分仓后这个错误会被写进对话记忆、二次固化。
