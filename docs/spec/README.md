# UI 契约库（spec）—— 唯一权威

> 本目录是 myco 面板化（无限抽屉）重做工程的**唯一权威规格来源**。
> 代码、`docs/design/`、`docs/reports/` 与本目录冲突时，**以本目录为准**；
> 本目录与真实实现/源码证据冲突时，**以源码证据为准并立即修本目录**。

## 0. 铁律

### G-00 禁止推测（最高优先级，veta 一切）

任何 spec 字段、任何实现代码，必须**先有依据**，再写。依据只有三种：

| 级别 | 含义 | 可用性 |
|---|---|---|
| `E0` | 源码 `文件:行` / 真机实测 / 用户明确拍板 | ✅ 唯一允许进入实现 |
| `E1` | 文档、issue、README 声称（未验证） | ✅ 可进 spec，必须标 E1 |
| `E2` | 推测、类比、"一般应用都这样"、"我觉得" | ❌ **禁止进 spec，禁止进实现** |

- 没有 E0/E1 依据的问题 → 写进 [open-questions.md](open-questions.md)，**停下来问用户**。
- 每个节点必须写**反证**：`如果不这么做会坏在哪`。写不出来 = 没理解 = 退回研究。
  - 范式：内滚到边缘**不许把残余速度传给外层**，因为用户会失去稳定观察点、页面乱滑、
    软件没能猜中意图 → 挫败。（见 G-04）
- **理解严格先于实现**。字段 1–13 无 E0/E1 依据、或反证不成立的面板，不得排进实现。
- **旧 myco 代码只是"现状证据"，不是"正确依据"**。参考实现的做法需要解释"为什么"，
  解释不了就标 E1 并进 open-questions。

### G-00b 单一事实源
一个节点的行为只在 `panels/*.md` 定义一次；代码/报告/清单只能引用 ID，不得另行描述。

## 2. 流程门禁

```
P0 契约（本目录骨架） → 用户确认
P1 事实库（并行只读：每参考实现一份 ref/*.md）→ 覆盖率对账
P2 归一取舍（每面板一张对照表）→ 用户逐项拍板
P3 面板 spec 定稿（panels/*.md）→ 自洽检查
P4 实现（按面板隔离）→ 真机 + 用户验收
P5 acceptance.md 打勾
```

**门禁指标**

- P1：源码可交互点命中数 vs 事实库条目数，差额逐条解释（不是 UI / 已废弃 / 重复）。
- P3：每面板 ① 每个可点节点有验收 ID；② 每个状态有布局描述；
  ③ 每个可展开节点声明展开形态（G-03）；④ 每条字段有依据级别。
- P5：`acceptance.md` 未打勾 = 未完成；截图/录屏缺失 = 未完成。

## 3. ID 规则

- 节点：`<面板>.<区域>.<节点>`，例 `chat.msg.thinking-header`、`settings.models.row-actions`。
- 验收项：`<面板大写>-<序号>`，例 `CHAT-12`。**一旦分配不复用、不改号**。
- 面板：见 [10-panels.md](10-panels.md) 注册表。
