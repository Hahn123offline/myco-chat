# P2 合并模板：每面板一张对照表

> P1 的 9 份事实库不能直接变成实现规格——必须先在**同一张表里横向对照**，
> 露出冲突，再由用户拍板。**这张表是 P2 的唯一产出，也是 P3 写 `panels/<id>.md` 的唯一输入。**

## 1. 表结构（每面板一张）

### 面板：`chat`

| 节点 ID | 参考A 做法 | 参考B 做法 | 参考C 做法 | 旧 myco | 冲突点 | 我的建议 + 理由 | 拍板 |
|---|---|---|---|---|---|---|---|
| `chat.msg.thinking-header` | DSH：不封顶+sticky（`ReasoningRow.module.css:6-22`） | dsh-Go：? | 太墟：? | 45% 封顶内滚（`ChatContent.kt:xxx`） | A 直接相反 | 选 DSH，理由见 G-03 | ✅ |
| … | | | | | | | |

**列的填写规则**

- **参考列**：只允许写事实库 `ref/*.md` 里已取证的内容，带 `文件:行`；没有该实现的做法就写「无」，
  不许写「大概也是这样」。
- **冲突点**：只写"两解互斥"的（如封顶 vs 不封顶）。不互斥的差异归「补充项」单列小节，
  不要混进冲突，否则表没法拍。
- **我的建议 + 理由**：必须引全局规则（G-xx）或给反证，不能写"感觉更好"。
- **拍板**：`✅ 采用建议` / `❌ 另选（写用户选择）` / `⏸ 待定（进 open-questions）`。
  未拍板的行**不得进入 P3**。

## 2. 面板产出检查单

每个面板合并完，必须能回答：

- [ ] 这个面板有**哪些节点**（ID 全列，不允许"其他"）
- [ ] 每个节点**选中了谁的做法**，拒绝的理由是什么
- [ ] 参考实现里有、但 myco 首版**明确不做**的，逐条列出并写出为什么（不能默默丢）
- [ ] 旧 myco 有、参考实现没有的（我方特色），逐条列出并确认是否保留
- [ ] 新增的全局规则需求（若有）→ 提进 `00-global-rules.md`
- [ ] 无法确定的 → `open-questions.md` 新增编号

## 3. 合并顺序（按依赖，不按重要性）

1. `base.primitives`（披露行、按钮、图标、动作条）—— 所有面板的地基
2. `base.layout`（无限抽屉壳、层叠、返回栈）—— 所有面板的容器
3. `chat`（最重，且依赖 1、2）
4. `sidebar` / `composer`
5. `model` / `attachment`
6. `settings`（壳 + 子页）

> 顺序理由：地基一旦拍错，后面每个面板都要返工；聊天页虽然最重，但它依赖披露行与容器契约。

## 4. 合并时的质量门

- 任一节点在 9 份事实库里**都找不到** → 说明是我方新设计，必须单列「新增节点」并说明依据（用户拍板）。
- 任一节点在三份以上参考里**做法一致** → 高置信，可直接建议采用，但证据仍要写全。
- 任一节点参考之间**互斥** → 不许"折中"，必须二选一并写反证；折中方案往往两边缺点都占。
