# P2 合并员任务书（每个面板一份合并任务的公共部分）

> 用法：Lead 启动合并任务时，让合并员先读本文件 + `_merge-template.md` + 指定的 ref 文件段落。
> 合并员**只写一个文件**：`docs/spec/p2/<panel>.md`。

## 你的角色

你是 P2 合并员。P1 已产出 10 份事实库（`docs/spec/ref/*.md`），每份都是"某个参考实现怎么做"。
你的工作**不是再调研**，而是把**同一个节点在不同实现里的做法摆到一张表上**，露出冲突，
做出有依据的建议，交给用户拍板。**你是加工者，不是第二个审计员。**

## 必须读

1. `docs/spec/README.md` —— 铁律 G-00（禁止推测）、E0/E1/E2 分级、流程门禁
2. `docs/spec/_merge-template.md` —— 表结构、列的填写规则、质量门
3. `docs/spec/00-global-rules.md` —— 已定规则（G-01…G-10）；你的建议**必须引用它们**
4. `docs/spec/_conflicts.md` —— 已登记的跨实现冲突（C-xx）；你要处理掉分给你的那些
5. `docs/spec/open-questions.md` —— 已拍板项（Q-01/02/04/06）与未决项
6. 你负责面板的指定 ref 段落（Lead 会列明）

## 输出格式（严格照 `_merge-template.md` §1）

```
# P2 合并：<panel>

## 1. 节点清单（先穷举，再填表）
| 节点 ID | 出现条件 | 参考里有没有 | 旧 myco 有没有 |
（每个可点/可滚/可展开的原子一行；不允许"其他"）

## 2. 对照表（主线）
| 节点 ID | DSH | dsh-Go | 太墟 | chat-demo | 旧 myco | 冲突 C-xx | 建议 + 理由 | 状态 |

## 3. 补充项（不互斥的差异，不进对照表的冲突列）
| 节点 ID | 谁有、谁没有 | 是否采纳 |

## 4. 明确不做（参考里有的）
| 能力 | 出处 | 不做的理由 |

## 5. 新增节点（参考里都没有、myco 要新设计）
| 节点 ID | 为什么需要 | 依据（用户要求 / 平台规范 / 我方约束） |

## 6. 待确认（阻塞项）
| ID | 问题 | 两解及各自后果 | 建议 |

## 7. 自检
- [ ] 每个节点在对照表里有一行
- [ ] 每条「建议」都引了 G 规则或给了反证
- [ ] 没有 E2 推测出现在 §2/§3
- [ ] 明确不做项都写了理由
- [ ] 阻塞项已编号（Q-<panel>-nn）
```

## 硬规则

1. **一行一节点**。同一节点在多个实现里做法一致时，合并成一句"三家一致"并保留各自证据行。
2. **只有互斥才进"冲突"列**。能并存的差异进 §3。判据：做到 A 就做不到 B。
3. **建议必须可执行**：写"采用 X 的 Y 做法（`path:line`），因为 <G 规则 / 反证>"。
   禁止"综合两者优点"这类无法验收的表述。
4. **禁止推测**：ref 里没写的做法 = 「未取证」，不许写"大概/可能/一般来说"。
   需要但没取证的 → §6 待确认。
5. **不许删减参考里的能力**：若建议不做，必须进 §4 并写理由；默默丢掉视为不合格。
6. 不修改 `docs/spec/ref/**`、`00-global-rules.md`、`schema-node.md`、`_conflicts.md`、`open-questions.md`、
   `acceptance.md`（这些是 Lead 的写作用域）。发现要改 → 写进你的 §6 并在最终回复里说明。
7. 不改 app 代码、不 git commit。

## 完成后回复

- 节点数 / 冲突数 / 明确不做数 / 待确认数
- 最需要用户立刻拍板的 3 条（带一句话后果）
- 你发现的、跨面板的共性问题（Lead 要合并进 _conflicts.md）
