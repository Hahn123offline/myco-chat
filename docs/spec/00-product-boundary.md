# 产品边界：myco 是「基座平台」，不是 work 套件

> 用户 2026-11-27 明确：
> **「myco work 和这些应用功能更加接近，需要重点区分功能边界：我们做的仍然是基座，
> 是一个支持和拓展能力很强的平台，没有正式引入 work 的完整功能。
> 你就把它理解为一个连 agent 工具不全的 DSH 手机版。」**
>
> 这份文件是**范围裁决表**：任何功能要不要做、做到什么程度，先查这里。

## 1. 一句话定位

- **myco** = **agent 基座 + 强扩展点**：能聊天、能跑 agent 工具（不全）、能装载面板与能力，
  **但不把"工作套件"搬进来**。类比：**"agent 工具不全的 DSH 手机版"**。
- **myco work**（另一个产品方向）= 更接近 Droid / 各类 agent 工作台：代码树、Diff、构建、终端、
  工作流、多 Bot、项目工作区——**这些属于 work，不属于本仓库首版**。

## 2. 裁决规则（按顺序判）

1. 它是否是**聊天/agent 交互本身**的一部分？（消息、思考、工具调用、输入、模型、附件、会话）
   → **是 → myco**
2. 它是否是**扩展点**（让别人能加东西）？（面板注册、工具渲染注册、provider、能力清单）
   → **是 → myco（做接口，不做完整实现）**
3. 它是否是**工作套件能力**？（代码/构建/终端/git/工作流/项目/多 Bot 市场）
   → **是 → myco work**（本仓库只留扩展点，不做功能）
4. 无法归类 → 写进 `docs/spec/open-questions.md`，**不得默认塞进首版**。

## 3. 归属表（已归位）

| 能力 | 归属 | 本仓库的处置 |
|---|---|---|
| 聊天 / 轮 / 消息 / 思考链 / 工具卡 | **myco** | 首批面板 `chat` |
| 会话导航 / 搜索 / 分组 | **myco** | `sidebar` |
| 输入区 / 附件 / 模型与推理档 | **myco** | `composer` / `attachment` / `model` |
| 设置（通用/模型/会话数据/关于/诊断） | **myco** | `settings` |
| 面板壳（覆盖栈、邻接、层叠） | **myco**（**核心扩展点**） | `base.layout` |
| 工具渲染注册 / 面板注册 / 能力清单 | **myco（接口）** | `base.primitives` + 扩展点 |
| 计划 / 目标 / 作业 / 定时 / 子代理 / 技能 | **myco 的扩展位**，首版不实现 | 注册位留出，面板标注 ⏸ |
| 工作区 / 项目 / 文件树 / Diff / 构建 / 终端 / git | **myco work** | ⏸ 不实现（见 `10-panels.md` §4） |
| 多 Bot 市场 / 工作流编辑器 | **myco work** | ⏸ 不实现 |
| 插件市场（第三方插件安装管理） | **myco work**（依赖 work 的运行时） | ⏸ 不实现；只保留本地扩展点 |

## 4. 对设计与实现的三条硬约束

1. **所有"工作套件"能力必须走扩展点，不许硬编码进基座**：
   面板通过注册表挂载、工具通过渲染注册表挂载。基座不认识"git/构建/终端"这些词。
2. **"工具不全"是明确状态而非缺陷**：工具清单可以少，但不能少到用户以为坏了；
   每个缺失工具在 UI 上要有明确说明或降级（不静默失败）。
3. **不因参考实现有某能力就加**：参考对象（dsh-Go / 太墟 / DSH web）都带 work 味的功能，
   **一律先过 §2 裁决**；`p2/*.md` 的「明确不做」清单即按此产出。

## 5. 与"候选功能"的关系

用户点名的新增（如 **DeepSeek 式"最近照片"附件面板**，见 `ref/deepseek-app-attachment.md` D-17）
属于"体验增强"，**不保证转正**。处置：
- 规格里照常写清（否则实现时无从落地），但**标 `candidate`**，并在 P4 排期上排在"已有功能对账"之后；
- 若最终不采纳，删除对应节点与验收项，并在此表登记"已否决 + 理由"。
