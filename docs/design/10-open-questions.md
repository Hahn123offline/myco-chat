## 原始问题（第一轮提问记录）

## D1【阻塞】宿主形态：myco 跑在哪，第一版给谁用？

| 选项 | 得到什么 | 代价 |
|---|---|---|
| **A. 本地 daemon（Node/TS）+ Web 客户端，桌面先跑** | 迭代最快；手机浏览器可先用；后续 Android 只是换壳；Work 的 proot 只是又一个工具后端 | 手机上「常驻陪伴」要靠后续壳；Node 进程的耗电/后台存活要单独解 |
| B. Android 原生（Kotlin/Compose）先做 | 直接贴合最终形态（无障碍看屏、相机、proot、后台常驻）；trace-memory 已证明用户这套 Kotlin 工程能跑 | 插件框架、provider 管理、agent loop 全部要重写一遍；TS 生态（MCP、工具）用不上；桌面版要另做 |
| C. 双端同一内核（本地 daemon + 多客户端），Android 用 nodejs-mobile/Termux 承载 | 只有一份内核逻辑；「一个她」跨设备天然成立 | 工程复杂度最高；手机上的 Node 运行时是长期风险点 |

**我的倾向：A，且把内核边界定成「可被任意客户端连接的本地服务」**，为 C 留路。
理由：MVP 要验证的是「框架能不能长功能」，不是「手机后台能不能常驻」。后者是 I4 之后的问题，
而且如果内核是 daemon 形态，Android 壳可以先用 WebView 连本机 daemon，再决定要不要原生重写。

**影响面**：语言（TS vs Kotlin）、UI 技术栈、插件加载方式（动态 import vs DexClassLoader）、
后续所有阶段的估时。**这条不定，I0 无法开工。**

## D2【阻塞】框架归属：自研内核，还是寄生 DeepSeek Harness？

| 选项 | 得到什么 | 代价 |
|---|---|---|
| **A. 自研薄内核（~600–800 行）+ 抄 dsh-icl 的纪律，不抄它的六抽象** | 产品形态完全自主（首屏、预设、插件面都是自己的）；无版本绑定；可移植到任意宿主 | provider 管理、会话、loop、工具管线都要自己写（但都不难，且参考代码齐全） |
| B. 寄生 DSH：myco = 一个 DSH preset/插件集 | loop/会话/权限/工具协议/沙箱全白送，1–2 天能出可聊天的东西 | 产品首屏被宿主污染（56% 是 coding-agent 脚手架）；被 DSH 0.2.x 内部 API 绑死（前代 `bridge.mjs` 1543 行就是教训）；手机上基本没戏 |
| C. 直接用 DSH 已发布到 npm 的包组合 | 比 B 更松耦合，但仍受其抽象与版本节奏牵制 | `@deepseek-ai/dsh-*` 多为 `0.0.1-rc`/`0.1.0-rc`，API 不稳；拼装文档要自己补 |

**我的倾向：A**，但**借鉴 B 的思路做验证**：先花 1 天用 DSH 跑一遍「provider 配置 + 多会话 + 简单工具」
当参照物，确认我们对「最顺手」的理解一致，再回来写自己的。
理由：你要的是「像 DSH 自身一样的一切皆插件框架」，而且最终形态是手机常驻伙伴——这两条都和寄生天然冲突。

**影响面**：决定 I0 是不是从零开始。**这条不定，代码一行都不该写。**

## D3 chat / work 的切割方式

- 选项：①一个 app 两个**预设**（同一份内核，不同插件白名单 + 不同 stateDir）；②两个独立 app。
- 证据：前代证明了「单人格/单焦点」与「多会话」在同一份 state 上不可兼得（`HISTORY.md:85-89`）。
- 倾向：**①**，`chat` 预设 = 单会话视图 + 人格 + 主动性 + 记忆；`work` 预设 = 多会话 + 工具 + proot 后端 + 只读共享记忆。
  两个 stateDir，一个只读共享记忆层（后期再做）。
- 影响面：预设机制必须在 I0 就有（白名单 + 配置差异），否则后期要动内核。

---

## D4 MVP 的能力边界：先到 I2 还是先到 I3？

- 选项：①I0→I1→I2（provider + 多会话 + loop）就交付第一版；②一路做到 I3（最小记忆）再交付。
- 证据：前代教训是「广度先于深度」，但也证明了**没有记忆的对话没有陪伴感**。
- 倾向：**①只到 I2 就给自己用起来**，每天用它聊天，用真实使用暴露 loop 的问题；I3 紧随其后。
  「先能每天用」比「功能齐」重要，而且真实使用数据是 I4/I5 的唯一依据。
- 影响面：三周排期切点。

---

## D5 Provider 抽象要不要把 Anthropic Messages 当一等协议？

- 证据：DeepSeek 官方已提供 `https://api.deepseek.com/anthropic`（Messages 协议对普通 API key 开放），
  DSH 的官方适配器走的就是 Messages；同时 OpenAI Chat Completions / Responses 也在。
- 倾向：**要**。三套协议各有字段差异（尤其思考模式、工具结果回传），混在一个 codec 里悄悄降级是事故源。
  但 MVP 只保证 `openai-chat` 完整可用，另两个协议先做「能连能流式」，怪字段豁免。
- 影响面：`packages/llm` 的结构（codec 抽象、profile 的 `endpointStyle`）。

---

## D6 记忆 schema 现在定死吗？

- 证据：前代最大的返工来自数据模型（v1→v2→v3，v2 被用户亲手否定）。
- 倾向：**现在定最小七表 + 三条不可逆决策**（`(ns,key)` 唯一索引、`source_row` 来源分类、
  `data.scope={owner,conv}` 会话维度），其余字段允许 later migration。理由：这三条改起来要重写数据，
  其它都是加列。
- 影响面：`packages/memory` 的 DDL 能不能一次写对。

---

## D7 隐私与出网：MVP 就要唯一出网点吗？

- 证据：trace-memory 的结论是「价值在唯一出口 + fail-closed + 审计，不在命中率」；
  而前代实测掩码 583/592 条未改、命中率趋近 0。
- 倾向：**MVP 只做「唯一出网点」的壳 + 日志**（所有模型/网络请求过一个 `egress.check()`），
  不做内容级脱敏。等真的有屏幕记忆再上 guard/masker。
- 影响面：provider 调用层要不要统一包一层（现在包成本最低）。

---

## D8 「看屏幕」的接口什么时候留？

- 证据：桌面端可连续捕获、手机端 1s 硬限 + MediaProjection 授权成本；前代常驻 1fps 已被否决。
- 倾向：**I0 就在 `capabilities` 里定义 `perceive.snapshot` / `perceive.capture` 两个槽位形状**，
  但不实现任何 provider。这样以后加「看屏幕/看相机」是加法，不是改内核。
- 影响面：零（只是两个类型定义 + 一个未绑定槽的启动告警）。

---

## 已按倾向默认采纳（你不反对就这么定）

下面四条有足够证据支撑、且改动成本低，我按倾向写进了简报，不再单独占用你的决策：

1. **人格 = 全局常量（代码/配置），关系 = 每会话数据**。人格 3.9k 字符，复制到 N 个会话只会让「一个她」变成「N 个她」。
2. **记忆 = 全局库 + `data.scope={owner, conv}`，检索默认全局**；`cursor` 必须 per-session。
3. **不 vendor cordis 全栈**：自己写 400–600 行内核（注销器 + 服务键 + inject + 事件分发）。cordis 核心 4.1.0 已发布，等 DI 真的变痛再换，接口不变。
4. **主动性 L3（无由头主动）默认关**，先只跑 L1（有人等）；L3 要单独预算 + 归属日志 + 人工抽检才开。
