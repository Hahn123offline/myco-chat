# MVP 闭合计划（先可用，再 I2 记忆）· 2026-11-26 讨论稿

> 用户方向：**先把 MVP 做成能日常用的闭环，再加 I2 记忆**；基本功能（DeepSeek 附属 API + 工具、拍照/相册/文件、
> 会话管理与搜索、更好的设置页）优先验证；UI 至少对标 DeepSeek chat 原版；设计令牌与控件要稳定。
> 记忆的两种形态（chat/work）可能不一致，**暂不快速推进**。

## 0. 判断

**方向合适，而且比直接进 I2 更稳。** 理由：
- 记忆是"慢变量"，需要真实使用数据才能设计对；而工具/媒体/会话管理是"每天都会碰到"的高频面，先闭环能立刻用上，也能暴露 loop 的真实问题。
- 没有真用起来的记忆层，只能靠想象做评测，容易重演前代"功能很全但没用起来"。

**但有两个顺序调整建议**：
1. **"设计令牌 + 基础组件"现在做**（不是美化，是**契约**）：只做色板映射、状态、尺寸、错误态，不做插画/动效。否则后面每个页面都会返工。
2. **工具循环（tool loop）必须排在媒体之前**：没有真正的 tool-call 执行，web_search/拍照/文件都只是摆设；先打通"模型要求调用 → 执行 → 结果回灌 → 继续"。

## 1. 当前真实差距（诚实清单）

- **Bridge 里还没有执行工具**：`ToolRegistry` 注册了 `time_now`，但 chat loop 从不调用工具，也没有把 tool schema 发给模型。这是本轮最大缺口。
- 会话只有 create/list/events；**没有 rename/delete/搜索**。
- 附件/拍照/相册/文件**完全没接**；DeepSeek 附属 API（search/fetch/ocr/asr/tts）只调研过，没接。
- 设置页有 provider CRUD，但缺"默认模型/角色选择、外观、数据管理"。
- chat/work 尚未分叉 UI：现在是同一个多会话壳。

## 2. 里程碑（建议顺序）

### M1 设计地基与易用性骨架（约 3–4 天）
- 落地 `50-visual-tokens.md`：`MycoTheme` + `LocalMycoColors` + 基础组件（按钮/输入框/列表项/气泡/空态/错误条）。
- 设置页重构：分组（模型 / 外观 / 数据 / 关于），provider 卡片交互打磨。
- **验收**：所有界面无硬编码 hex；浅/深/跟随系统三档截图；空态/错误态齐全。

### M2 工具循环（约 4–5 天）
- 两个方言都支持 tool calls（OpenAI `tools/tool_calls`；Anthropic `tool_use/tool_result`）。
- Bridge 执行工具 → 结果回灌 → 继续到上限步数；`tool/call`/`tool/result` 事件落盘；预算（schema 字符）进测试。
- **验收**：一个纯本地 `time_now` 工具在真机上被模型调用并返回结果；工具失败带 reason，不静默。

### M3 DeepSeek 附属能力（约 2–3 天）
- capability provider（search/fetch/ocr/asr/tts）+ 工具面：`web_search`、`read_url`、`ocr_image`、`transcribe_audio`、`speak`（TTS 可后置）。
- 每条能力有成本/限额声明；`web.search` 优先。
- **验收**：真实调用一次 web_search 并在对话里引用来源；失败/限流有明确错误。

### M4 会话管理与搜索（约 2 天）
- rename/delete（软删）+ 会话内/跨会话搜索；事件日志加索引字段。
- chat 模式：默认单焦点（隐藏多会话入口，抽屉先留空/预留"另一个界面"）；
- work 模式：保留多会话。
- **验收**：搜索能定位历史消息；chat/work 通过一个配置切换，共用同一套存储。

### M5 媒体与附件（约 3–4 天）
- 拍照/相册/文件选择 → 附件 → 存储与消息关联；图片走视觉模型（deepseek-flash 支持图像），文件走文本/截断策略。
- 权限（相机/相册/通知）与失败兜底；隐私：默认本地、不自动上传。
- **验收**：真机拍照 → 发消息 → 模型描述图片；相册选图/文件选择同样可用。

### M6 视觉细化（约 2–3 天，可穿插）
- 基于 M1 稳定组件做排版、暗色发光规则、空态插画（若有）、微动效。
- **验收**：与 DeepSeek chat 并排截图对比；关键路径三步内完成。

## 3. 暂不做（明确写死，防止偷偷加）

I2 记忆/召回、人格卡、主动性、感知（屏幕/相机常驻）、work 的重后端（proot）、多设备同步。

## 4. 关于 chat/work 的记忆分歧（风险记录）

- 共享的是 **schema/来源分类/存储**；不自动共享"写入策略"。
- chat 的连续叙事 vs work 的任务片段，读取与写入都要有 app 维度；宁可先各写各的，也不要过早合并。
- 任何"跨 app 自动吸收"都必须有开关与可见的 provenance。

## 5. 关于 UI 两条路线（用户的两难）

| 路线 | 优点 | 代价 |
|---|---|---|
| A. 先易用/逻辑，后美化 | 快，功能验证优先 | 后期整体返工风险高 |
| B. 一次做好看再复用 | 视觉稳定，后期省事 | 现在功能还在变，容易过度设计 |

**建议中间路线**：现在做"**地基级视觉**"（令牌/组件/状态/排版网格），不做"装饰级视觉"（插画/动效/渐变细化）。
理由：地基的返工成本最高，装饰的返工成本最低。

## 6. 验收方式

- 我用 adb 脚本驱动真机（点击/输入/截图）+ 你实际点一遍对照；
- 每个里程碑给：截图、测试数、一次真实调用记录（含 cost）、已知缺口；
- UI 对标：与 DeepSeek chat 原版并排比较（首屏、会话列表、输入区、设置页、错误/空态）。
