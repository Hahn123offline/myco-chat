## D1 宿主形态：A（桌面 daemon + Web 先跑）

**用户**：选 A，认同"耗电与存活"要考虑。

**含义**：第一版是可被任意客户端连接的本地面板（Node/TS）+ Web 客户端；
**但整个设计按移动端原生来做**（用户原话：整个 app 的设计都围绕移动端原生的目标进行；
桌面端的定义"略微尴尬"）。

**影响**：
- 初始化实现（I0–I2）跑在 Windows，但 UI 采用移动优先（单列、触摸、无 hover 依赖、安全区、键盘弹出布局、通知优先于 toast）。
- 内核不持有任何"桌面专属"假设：无绝对路径入库、无窗口概念、无系统菜单依赖、无多窗口假设。
- 手机壳 = 客户端，不重写内核；后续可选 WebView 壳 / 原生壳 / 内嵌运行时（见 D-mobile 待定项）。
- 耗电与后台存活是**产品级需求**，不是优化项：常驻轮询、无障碍常驻、WebView 常驻都要在架构上可关。

## D3 chat / work：两个独立 app，共享存储，各按自己的策略读取

**用户**：建议 ②（两个 app），但**共享记忆文件，按各自策略读取**。理由：
- 两边功能差异大、目标形态不同；
- chat 里看不到 Linux 管理、看不到多会话，专注一个**连续的单焦点 agent 角色**；
- work 里不会产生记忆混乱的风险。
- MVP 挑"二者的共享初始形态"做；work 更符合传统 agent 形态（DSH 手机移植里有很多成熟实现，但用起来不习惯）。

**含义（工程化）**：
- `~/.myco/store/` = 共享区（sessions / memory.db / personas / delivery）；
  `~/.myco/apps/chat/`、`~/.myco/apps/work/` = 各 app 自己的设置、默认模型、UI 状态。
- **存储格式只有一份**，读取策略是 app 层契约（这就是"共享初始形态"）。
- chat：单一连续会话（不 fork、不新建、不切换；只压缩与归档），人格卡唯一所有者，主动消息唯一发出者。
- work：多会话、可 fork、任务型；人格卡可**只读同步**（要拿来当 chat 用也可以，但设计不匹配）；**不主动发消息**（只发任务完成通知）。
- 共享 = 同一份 memory.db + 同一份 provider/凭据；差异 = 读过滤、注入策略、会话数量、权限面、通知权。

## 第二轮补充修正（2026-11-25 21:00，覆盖冲突处以此为准）

### A1 人格卡：独立组件 + 单向复制同步 + 版本化，禁止互锁

**用户**：人格卡只在 work 中提供「快速单向同步通道」；两边的卡都是独立组件、都保留完整功能，work 改卡改的是 work 的副本。
原则是**共享资源但尽可能不互锁**——两个 app 不一定同时装在同一台手机上（虽然大概率是自己用，但不考虑这些情况是错的）。

**设计含义**：
- 人格卡成为**带版本管理的模块**：`cards[]`（多卡）+ 每卡 `versions[]`（历史、回滚）+ `activeCardId`。
- 每个 app 持有自己的副本与激活指针；**同步 = 一次性复制生成新版本（单向）**，不是共享文件、不是双向合并。
- 同步来源用 `cardId + version + contentHash` 标识；目标端新建/更新本地版本，并记录 `source: {app, cardId, version, hash}` 供溯源。
- 互锁禁令：任何一方离线、未安装、版本陈旧，都不影响另一方启动与改卡。

### A2 修正 D4：平替官方 chat **需要多会话**

**用户**：常用 chat app（不是 myco chat）就是"会话列表 + 聊天框 + 设置页"；DeepSeek 开源过 chat app demo，大概就长那个样。

**含义**：
- **MVP（I2）交付的是常规多会话 chat**：会话列表、聊天框、设置页三件套，能直接平替限额的官方 chat。
- "单焦点 / 连续角色 / 会主动"是**人格与主动性层**的属性（I4 起），不是"UI 上只能有一个会话"。
- 之前 D3 写的"chat 看不到多会话"修正为：**chat 不做多会话管理工具**（无工作区、无 fork、无并行任务视图），但保留常规会话列表。
- 会话数据模型从一开始就是多会话（与 D3 的 work 共享同一份引擎），chat 只是 UI 呈现更简单。

### A3 proot 分发：同意暂不定；侧载是常见路径

**用户**：目前最常见的思路之一就是侧载；同意不现在定。到时候学习社区实现，比如 DSH GO 和太墟（都是 GitHub 项目，大概率侧载）。

**含义**：work 的 Linux 后端先按"侧载分发"作为默认假设，Play 渠道内测版不含 proot；
I5 之前研究 DSH GO / 太墟 的实现再定（记录在 [runtime-options](recon/runtime-options.md) 之后）。

### A4 离线独立：**硬要求**，不是偏好

**用户**：应用应尽可能离线，**不应该依赖任何远程主机才能运行本体**。chat 和 work 都能单手机运行；
没有远程电脑 ≈ 零影响，仅 work 没有第二设备可用。桌面 daemon 只作为开发/预览载体。
明确提醒：不要默认"电脑后端 + 手机连接"；不希望留下任何难还的技术债。

**含义（覆盖此前一切相反假设）**：
- 手机端必须能独立完成：provider 调用（直连模型服务）、会话存储、agent loop、记忆、通知、主动性。远端设备是**可选增强**，不是运行前提。
- 桌面 daemon 的定位降级为：**开发/预览/测试载体**；不得成为手机上任何功能的必需依赖。
- 因此 D9（内核载体）的评分第一维是"离线独立"，任何"必须连远端"的方案直接出局。
- 同步/多设备是后续可选能力，设计上要避免"只有连上才完整"。

### A5 GUI 必须模块化：无 GUI 后端照跑，多 GUI 可整体替换

**用户**：GUI 是不容小觑的点（第一印象大多毁在这）；一开始 GUI 架构就要有清晰约束、或者模块化——
没有 GUI 后端照跑，多个 GUI 模块随时换（不只是换色，重写一套都行，只要符合接口）。

**含义（写进架构约束）**：
- 核心与 GUI 之间只通过一个 **Bridge 接口**（命令 + 事件 + 查询），GUI 是实现该接口的独立模块。
- Bridge 至少两种传输实现：**in-process**（手机/桌面原生 UI 直连，不开本地服务器）与 **HTTP/SSE**（浏览器/远程客户端）。
- 必须有一条测试：**headless 模式**（不加载任何 GUI 模块）下核心能完整跑一轮对话。
- GUI 模块可整体替换：ChatGUI、WorkGUI、WebGUI、TUI 各自实现同一套 Bridge 客户端契约；不共享组件库是允许的。

### A6 同步模型（人格卡 / 模型 profile / 以后的记忆）：快照 + 本地日志 + 单向拉取

**用户要的四条**：各管各的 · 能一键读取对面 · 同步到对面需二次确认 · 两边各不冲突的撤回。
在此基础上补全为可实现的机制：

**数据形态（两边完全同构）**
- 每类对象（`persona-card` / `provider-profile` / `capability-provider` / 以后 `memory-item`）都有：
  `id` + **不可变版本链** `versions[]`（每版含 `version`、`contentHash`、`payload`、`createdAt`、`origin`）+ **本地激活指针** `active`。
- 每边维护 `journal`（本地操作日志）：`{opId, at, kind, id, action, before, after, remoteRef}`。
- **不存在共享可写状态**；两边各自持有完整副本，互不为前提。

**跨 app 传输（D10 的"显式同步"）**：`myco.sync/v1` 导出包
`{ schema, sourceApp, exportedAt, cursor, objects: [{kind, id, version, contentHash, payload}] }`。
MVP 用**文件导出/导入**（系统文件选择器）；以后可加二维码/同签名通道，但都不是必需。

**三个动作**
| 动作 | 语义 | 确认 | 可撤回 |
|---|---|---|---|
| **拉取（一键读取对面）** | 导入对方的包 → **预览 diff** → 选择要应用的条目 → 在本地**新建版本**（绝不覆盖） | 一次（本地应用） | 是（本地 journal 反向：指针回退 + 版本标记 superseded） |
| **推送（同步到对面）** | 选择条目 → 生成导出包 → 交给对方 | **两次**：导出方确认"要推送哪些"，导入方确认"要应用哪些" | 是（双方各自 journal；撤回只影响自己） |
| **撤回** | 只回滚**本机**的指针/版本，**绝不改写对方** | 一次 | 自身可再撤回（journal 双向可重放） |

**冲突规则**：同一 `id` 两边都改过 → 不自动合并；预览里显示"双方都有新版本"，用户选择
保持本地 / 采用对方版本 / 两个都保留（版本链允许分叉，UI 显示分叉）。**任何情况下不丢版本**。

**密钥边界**：模型 profile 同步只带 `auth.ref`（如 `DEEPSEEK_API_KEY`），**永不同步密钥值**；
导入方若缺该引用，标"需要本机补 key"，profile 仍可用其它 provider。

**版本管理 UI 最小集**：卡片/档案列表 → 版本历史（时间、来源 app、hash 前缀、备注）→ 激活/回滚/对比。

### A7 常驻：不要求长时间挂着手机，"尽力而为"是一等公民

**用户**：手机可能没法长时间常驻，仅告知；有好的替代方案也可以安排。

**设计**：
- **不承诺 24/7 在线**。核心在进程存活时工作；后台靠 FGS + 通知尽力维持。
- **打开即追平**：启动时重放未读/积压；主动消息**合并成一条摘要**，不补发一堆通知。
- **定时检查尽力而为**：WorkManager/AlarmManager（≥15min，Doze 会延迟）只在"有值得说的事 + 空闲够久"时提醒；
  没有就不产生 turn（前代 68% 空转的教训）。
- **产品措辞要诚实**："打开时她一定在；不打开时是尽力而为"——不写"24 小时在线"。
- **可选替代（不依赖）**：以后可把同一内核跑在旧手机/迷你主机/云电脑上，手机作为客户端连它；
  这是**增强**，不是运行前提（A4 不变）。
- `doctor` 要报：电池优化是否白名单、FGS 状态、上次心跳/检查时间、国产 ROM 自启动引导链接。

## 方向留底（不是最终设计，用户明确要求"留底"）

### F1 myco chat 的定位
- 类比 **ICL 独立版**：优势是**绝对干净的单会话**。
- 多会话 + 单人格是社区普遍难解问题，**不挑战**。
- 一句话："为了那一个角色存在，一个绝对连续的角色，一个会主动的陪伴。"

### F2 myco work 的定位
- "有一部分 chat 的功能和实用特性（比如实时视频交互），共享聊天记忆，不关心焦点单一，本质是 agent。"
- 支持人格卡、支持同步 chat 的人格设定（理论上可以当 chat 用，但设计不匹配）。
- **手机上的意义大于电脑**：现有手机 agent 功能耦合多、操作反人类、或整个进程依赖后端 Linux 跑完整 DSH；电脑上的 work 写出来大概只是"简陋版 DSH"。
- 分层能力设想：
  - 日常内部轻任务：模型直接输出**可交互 HTML**、调计算器、跑简单脚本、上点网；
  - 更重任务：按需启动 Linux（proot）跑命令、拉仓库；
  - 同一套无障碍能力 → 手机 computer use（社区有成熟开源实现）；
  - 共享 chat 的数据、看屏幕等特性。
- 目标不是全栈开发；"轻 work"在日常任务上效果最好。
- ⚠ **proot 与分发（调研发现，I5 前必须定）**：运行时下载 rootfs / 可执行文件在 Play 渠道大概率违规（Termux 自身因此长期卡在 targetSdk 28）。
  两条路：① 按 APKLF 思路把可执行文件塞进 APK native libs；② work 走侧载 / F-Droid / GitHub 渠道，不进 Play。这条不影响 I0–I2。

### F3 多设备 / 远程工作区（远）
- 支持配置多 device / 云电脑；一个工作区列表可能在不同机器；机器不在也能继续对话。
- 架构选择：**不在电脑跑 agent loop 让手机连，而是手机连接对应 device**。
- 现状：主用 sakura frp 的 HTTPS 隧道连自建服务。
- 对现在的约束：事件日志要同步友好（ULID、单调 seq、无绝对路径、时钟偏移容忍），`workspaceId/deviceId` 字段现在预留，不实现。

### F4 移动端原生原则（贯穿）
- 交互：单列流、大按钮、语音优先、通知即入口、断线可恢复、无"桌面悬浮窗"依赖。
- 资源：常驻进程必须有"静默档"；感知默认关；轮询改为事件/推送；每项能力标注耗电成本。
- 数据：所有写入先落本地、可离线、可重放；不做"必须在线"的功能。

### F5 移动端硬约束（来自 `docs/recon/mobile-agent-landscape.md`，I0 起写进契约）

| # | 约束 | 类型 |
|---|---|---|
| 1 | 常驻 = FGS `specialUse` + 常驻通知 + 用户白名单；别用 `dataSync` 当常驻（6h/24h 上限） | 硬限制 |
| 2 | 主动找人只能走通知（本地或 FCM）；后台 socket 长连不能当唤醒机制 | 硬限制 |
| 3 | 截图/感知 = 事件 → 去抖 → 单帧；`takeScreenshot` ~333ms 平台限速，错误码要分类 | 硬限制 |
| 4 | MediaProjection 只做用户显式开启的短会话，不做常驻感知 | 硬限制 |
| 5 | 后台不能开摄像头/麦克风；语音陪伴必须前台交互 | 硬限制 |
| 6 | proot/Linux 后端不能靠"运行时下载可执行文件"分发 | 硬限制（Play 政策） |
| 7 | 移动壳内核选型：Kotlin/JVM 优先，不默认背 Node/React（与 D9 绑定） | 经验 |
| 8 | 事件日志：ULID/单调 seq + 无绝对路径 + 逻辑时钟，客户端离线可重放 | 经验 |
| 9 | 电量与配额是一等公民：WorkManager ≥15min、Rare bucket 24h 仅 10min；"用户在场才跑 loop" | 硬限制 + 经验 |
| 10 | 远程连接默认加密：绑 `*.nyat.app` 自动 HTTPS，检测到明文就拒绝/告警 | 安全硬要求 |

### F6 远程/多设备形态（用户方向留底）
- 手机连设备，而不是"电脑跑 loop、手机连它"的单一固定 PC 形态；工作区列表可指向不同机器（含云电脑）。
- 远程协议 = WS/SSE + 幂等事件；断线可重放；机器不在时 chat 仍要能用（**这条决定了 D9 的答案不能只是"全靠远端"**）。
- 现状：sakura frp 的 HTTPS 隧道。

## 第三轮候选（2026-11-25 21:15，待拍板）

### D9【推荐 A】运行时：Kotlin/JVM 单核心

调研产出：[runtime-options.md](recon/runtime-options.md)（244 行，含 7 候选、证据表、Play 政策、spike 判据）。

**推荐 A = Kotlin/JVM 单核心**：
- `core` 是纯 JVM Kotlin 库（Android 与桌面都跑 JVM）；Android 用 Compose 原生壳；桌面用 JVM + Ktor（HTTP/SSE）做开发/预览壳。
- 插件 = **编译期 Gradle 模块 + 运行时注册表**；按 KMP 结构预留（A/B 同栈，只改构建形态，不构成分歧）。
- 五维加权：A 89 / B 88 / F 74.5 / G 70.5 / C 70 / D 61.5 / E 58.5。

**三条决定性理由**：
1. 离线单机所需能力（FGS `specialUse`、通知、无障碍、SQLite、Keystore、文件）**全是 Android 原生 API**；RN/Flutter/内嵌 Node 最终仍要写同一层 Kotlin 胶水，还额外背一个运行时（包体/内存/耗电/16KB/Play 政策）。
2. **前代代码是资产**：trace-memory 353 个非测试 Java 文件 / 110 测试，其中只有 78 个（22%）import `android.*`——Kotlin/JVM 是**移植**而不是重写；而 myco 仓库目前只有 docs + reference，现在换栈成本≈0。
3. Play 禁止运行时下载可执行代码（例外只有 VM/解释器且须 "indirect access"，如 WebView JS）→ 手机上的「一切皆插件」只能 = **编译期模块 + 运行时注册表 + 可下发数据插件**。这与 trace-memory 的 `Module` / `HostContext.effect()` 契约同构。

**否决证据（摘要）**：nodejs-mobile 官方 npm 仍是 18.20.4（2024-10，unpacked 375MB）；Node 22 仅社区 fork（libnode ~88MB/2 ABI）；`node:sqlite` 需 Node≥22.5 且实验；App Center/CodePush 2025-03-31 停服；RN 内置 fetch 无 `response.body`（SSE 要 native/polyfill）。

**影响**：
- 00-design-brief 与 30-i0-plan 里所有 TS/Node 落点要改成 **Kotlin/Gradle 多模块**；TS 只保留在"桌面 Web 预览壳"。
- 插件机制从"动态 import"改成"Gradle 模块 + 注册表"；插件市场若以后要，只能走侧载/自带渠道。
- I0 的 T0（语言无关契约）不变，仍是第一步；T1 起按 Kotlin 落地。

**用户反馈后的修订（D9 已拍板：A）**：
- **Play 论证降权**：中国大陆基本用不上 Google Play、也无上架经验，陪伴类 app 在国内被风控更严 →
  分发默认走 **侧载 / GitHub Releases / 网盘 / 国内渠道**。所以"Play 禁止动态代码"不再是硬约束，
  Kotlin 仍胜出是因为**原生能力、前代代码复用（78/22）、包体/耗电/开发速度**，不是政策。
- **动态插件：推迟，不现在做**。理由：用户几乎不用"自己改自己"；动态 dex 的成本是 classloader 隔离、
  API 版本兼容、供应链安全（侧载渠道尤其）、崩溃边界，收益却主要是"不重装换插件"——MVP 不需要。
  保留 `PluginLoader` 接缝 + 插件 API 版本号；以后若要做，优先 **APK 内资源随包加载**，不做运行时下载。
- **DSH-GO / 太墟 的"自己改自己"**：它们是"后端跑完整 Linux + DSH"，属于 work 的 proot 路径，不是 chat 内核；
  MVP 不碰，I6 再研究。
- **spike 改为 S0 walking skeleton**（不写一次性代码，见 I0 计划）：用真实产品代码跑通最小竖切，边建边测。

**分发约定**：签名密钥离线保存；先出 GitHub Releases（+ 可选用自建更新检查）；上架商店是后话。

**待你点头的只剩**：是否按 S0 顺序开工（T0 已交付，见 [specs](../../specs/README.md)）。

### D10【新】双 app 的安装与共享形态（Android 上不是免费的）

**问题**：Android 独立 APK = 独立 UID + scoped storage，`sharedUserId` 已废弃。所以"两个 app 共享记忆文件"没法直接成立。候选：

| 方案 | 独立性 | 共享实时性 | 代价 |
|---|---|---|---|
| 一包双 launcher 入口（一个 APK 两个图标） | 差（必须同时安装） | 完美（同 UID 同一份库） | 违背"两个 app 不一定同时存在" |
| 两个 APK，各自完整内核 + **显式导出/导入（增量游标 + 签名校验）** | **好（各自可独立运行）** | 最终一致（手动或后台同步） | 需要同步协议与冲突规则；认知上"共享"变成"同步" |
| 两个 APK + 同签名 **ContentProvider** 实时共享 | 中（缺一方时降级） | 好 | 跨进程 DB 并发、权限、双写者冲突；实现复杂 |
| 一个"core app" + 两个薄壳 | 差（core 是硬依赖） | 好 | 违背 A4（不能有必需依赖） |

**倾向**：**两个 APK，各自完整内核（都内置 core 库），共享 = 显式同步**（记忆条目/人格卡/事件游标，签名校验 + 幂等 + ULID）。
这样：离线独立成立、不互锁成立、两 app 不同时存在成立；代价是"共享"是最终一致的，不是同一份文件。
若以后确实需要实时共享，再上同签名 ContentProvider，且仅作为可选增强。

**D10 已确认**：采用"两个 APK、各自完整内核、显式增量同步"。
同步协议细节见 **A6**（版本链 + 本地 journal + 拉取/推送/撤回三动作）；传输 MVP 用文件导出/导入。
