# 观察日志与重建层 — 设计定型

> 状态：设计冻结（未实现）
> 日期：2026-11-21
> 取代：`trace_frames` 采集即定结构、`object_messages` 采集即归属、`lines` 硬投影

## 0. 这份文档解决什么

现在的 trace 层有三个纠缠在一起的问题：

1. **采集时就决定结构**：`object_key` / `page_title` / `kind` / `side` / `inferTitle` 全在采集或投影阶段做判断。
2. **判断错了不可撤销**：历史帧无法帧级归属，只能"接受遗留"。
3. **去重在查询期反复付费**：每个问题都要重新解一遍"这算不算同一条"。

根因不是规则写得不够好，是**判断发生的位置错了**。本文定分界。

## 1. 公理

**A1 采集层只记录事实，不产生判断。**
事实 = 系统 API 读到的值，或像素直接测得的量。
判断 = 任何"这属于什么 / 这是不是新的"的标注。

**A2 顺序免费，分段昂贵。**
时间戳给出全序，零算法。把观察切成"段"需要判断，且判断错了**连接永久丢失**。故分段一律后移。

**A3 重建是视图，不是事实。**
同一段观察，不同问题可重建出不同段。视图不落盘成真相，可无限重算。

**推论**：错误必须便宜。宁可重建得难看，不要采集时切错。

**A4 只要证据在，读者可以自己推。**
重建不必"自动就会"。采集层的验收标准是：**每个过渡类型，让读者推断所需的证据是否都在。**
（例：A 链在 B 站评论区 → B 链在 B 站主页，中间一次从屏幕右侧开始的左滑。
最终判断由 agent 做，采集只需保证三样都在：两次窗口/内容状态、滑动方向与起点、时间间隔。）

## 2. 职责边界

| | 采集层 | 重建层 |
|---|---|---|
| 做什么 | 采样、去重、追加 | 对齐、分段、叙述 |
| 判断 | 只有"何时记" | 有，但可撤销 |
| 输出 | observation（时刻采样点） | view（按问题生成） |
| 错了 | 漏采（可测、下次可补） | 视图难看（重算） |

**采集层禁止出现的字段**（含派生投影）：

```
object_key / page_title / title_candidate / kind / chain_id
side / sender / is_new_page / is_new_context / 任何"这是什么"的枚举
```

`Role` 七分类（PARAGRAPH / LIST_ITEM / BUTTON / TITLE / BADGE / INPUT / OTHER）**全部废弃**。
替换为 A11Y 直接给的布尔位：`clickable / editable / scrollable / checkable / focused / visible`。
前者是猜的，后者是读的。

`inferTitle()` **整个删除**（含 TITLE_NOISE 中文正则表、`top≤350`、`|top-170|/100`）。
`frameObjectKey()` **整个删除**（含 `y∈[80,400]`、`len 2–20`、chrome 词表）。

## 3. 观察日志 schema

### 3.1 observation

```
id            INTEGER PK
t_mono        INTEGER   单调时钟（对齐用，不受改时间影响）
t_wall        INTEGER   墙上时钟（叙述用）
pkg           TEXT
activity      TEXT      A11Y 给的 className，事实
window_stack  TEXT(json) [{pkg, cls, bounds, layer, focused}]，有序，事实
content_hash  TEXT      去重键
shot_ref      TEXT      NULL = 本帧未留全图
grid          BLOB      12×200 luma，位移测量用（形状由 §4.4 实测决定，不是正方形）
mean_luma     INTEGER
sharpness     REAL
n_nodes       INTEGER
n_text_nodes  INTEGER
elapsed_ms    INTEGER   解析耗时（自身成本可观测）
```

### 3.2 obs_nodes（每个"可读或可交互"节点；容器不单独存）

```
obs_id, idx             主键 + 树内序号
parent_idx              父节点序号（指向本表已存节点，最近的被存祖先）
depth
cls_id                  → dict_cls
resid_id                → dict_resid，0 = 无
text_id                 → dict_text，0 = 无文本
left, top, right, bottom
flags                   bitmask: clickable|editable|scrollable|checkable|focused|visible
scroll_x, scroll_y      仅 scrollable 有意义，其余 NULL
```

**`parent_idx` 是这一层最重要的新字段**：它让"这条消息属于哪个气泡 / 这个按钮属于哪个弹层"
从**事实**可推，而不是从坐标先验猜。这是现在 `sender` 只有 45% 的根因。

### 3.3 obs_input（输入事实，允许缺失）

```
obs_id, t, kind(CLICK|SCROLL|KEY), node_idx NULL, bbox NULL, dx NULL, dy NULL,
       source(BBOX_DIFF|EVENT|PIXEL|NULL)
```

`TYPE_VIEW_CLICKED` 的 `source` 节点给到 bbox → **点击目标的位置是事实**，不是猜的。

滑动位移：**三条候选路线实测后只剩一条半**（见 §4.5）：

```
1. NODE_BBOX_DIFF：同一节点（按 text / resource-id 匹配）前后 bbox.top 差，取众数
                   —— 实测 QQ 给出精确 897px；众数天然滤掉静态 chrome 与重绘异常
2. PIXEL：grid 对齐估出的 dy/dx（§4.4，误差 <5px）—— A11Y 不可读时的唯一路（微信）
3. 两者都无 → 显式 NULL（未知），不得写 0
```

`AccessibilityNodeInfo` **没有** scrollX/scrollY 读取器（`javap` 已确认），
`TYPE_VIEW_SCROLLED` 的 delta 是错的量级（bilibili 全 0、QQ 报 3 而实际 897）。
两者都不得作为位移来源；该事件最多算**弱触发信号**。

### 3.4 三值原则

字段缺失 = `NULL` = **未知**，不得当 0 / 空字符串 / "没有"。
下游必须能区分「不知道」和「确认没有」。宁可输出"未知"，不要输出错的断言。

### 3.5 字典化（前置条件，非优化）

不做字典化约 65MB/天，不可接受。字典化后约 11MB/天（活跃 3h、2s 一帧），30 天约 330MB。

```
dict_cls(id, s)      A11Y className，基数小
dict_resid(id, s)    基数小但长
dict_text(id, s)     长尾，但重复率极高（群聊、列表页）
```

估算依据：每节点 `idx/parent/depth/cls_id/resid_id/text_id/bbox×4/flags` ≈ 12B，
单帧约 100 个节点 ≈ 1.2KB + observation 头 ≈ 2KB/帧。

## 4. 采集策略（规则只允许住在这里）

采样由**可测的覆盖目标**驱动，不是固定频率。

### 4.1 两条覆盖目标

- **无空档**：任意两次相邻 observation 之间，若屏幕发生可见跳变而中间无第三次观察 → 记一次漏采。
- **有重叠**：相邻 observation 的 grid 在允许位移范围内能高相关对齐 → 可拼接。
  相关度低于阈值 → 记一次"无法拼接"（这是硬失败，不是软降级）。

两条都可离线回放测量。

### 4.2 触发源（按成本升序）

```
L0  A11Y 事件（免费）：沿用现有廉价前置过滤 + 300ms 节流
L0' 廉价探针（便宜）：只读 n_nodes + 文本集合 hash + scrollable 容器 cls/bounds
    —— 不做 bbox 提取、不建 PageElement、不跑 DangerSignals（见 §4.7 成本实测）
L1  高频采样判定：以 L0' 相邻两次的差量决定是否加采（内容集合变化 + 像素 dy）
L2  像素 grid 差量超阈值（A11Y 读不到的 App 的唯一信号：微信 / WebView / Canvas / 游戏）
L3  takeScreenshot 全分辨率（受系统 1s 硬限，实际取 1200ms 安全间隔）
L4  read_frame 按需现拍（保持现状）
```

L0' 与 L3 职责不同：**L0' 回答"该不该看"，L3 回答"看到了什么"。**

**注意**：不能假设 A11Y 可用。微信的树是空的（§4.6），对它而言 L2 是唯一信号源。

### 4.3 硬约束（已确认的事实）

- `AccessibilityService.takeScreenshot()` 是一次性请求，**无持续帧流**，系统最小间隔 1s
  （现有 `SHOT_MIN_THRESHOLD_MS=2000` 是留余量，`INTERVAL_TIME_SHORT` 即撞限）。
- 现有"变化率截图"是**事后分类器**：`HsvCutDetector` / `quickHash` 都在整屏成本付完之后才算，
  且每帧都跑 ML Kit OCR。它不省电，只给已花的钱贴标签。
- 故**不引入 MediaProjection**：它需要每次冷启动授权（Android 14+ 无法静默复用），
  对记忆常驻类应用是不可接受的 UX 成本。像素传感器保持 `takeScreenshot` 路线，受 1s 限约束。

### 4.4 实测：栅格形状（2026-11-21，MIUI V816 / Android 15 / bilibili 首页）

用 `screencap` 连取 3 帧（两次慢滑各前进约 372px），以 **A11Y 共享文本的 y 差**
作为位移真值（23 条共享文本，中位数 372/369/741px），比较各降采样形状的估计误差：

| 形状 | 1 行 | 误差 (dy) | 结论 |
|---|---|---|---|
| 8×16 方形 | 117.5px | −20 / −16 / −36 | **不可用于拼接**（量化误差 ≈1/3 行） |
| 8×60 | 31.3px | +4 / +7 / +11 | 勉强 |
| 8×200 | 9.4px | +4 / −2 / +2 | 够用 |
| 32×400 | 4.7px | −1 / +2 / +2 | 富余 |
| 120×600 | 3.1px | +1 / +1 / −2 | 过度 |

横向（把 s0 按已知 dx 平移，合成测试）：

| 列数 | 1 列 | dx 误差 |
|---|---|---|
| 8 | 150px | ±50 |
| 16 | 75px | ±25 |
| 48 | 25px | ±5 |

**结论：栅格必须不对称。**

- **dy 需要行数**（拼接接缝可见度直接由它决定）→ 行 ≥ 200（1 行 ≈ 9.4px，误差 <5px）
- **dx 只需要列数够分辨"是否发生大范围横移"**，不需要精确量 → 列 12（1 列 100px）足够
- 定：**12 × 200 uint8 = 2400B/帧**，PNG 压缩后约 1.2KB。粗变化 hash（8×8）由它降采样得到，不单独存
- 单用 8×16 会犯"用测变化的栅格去测位移"的错——两件事的精度需求差 30 倍

**拼接已验证可行**：3 帧按上述 dy 拼接得 1200×2659 长图，8 张卡片连续，
无重复带、无可见接缝；重叠区（1546px）平均像素差 11.0/16.4，差异集中在视频缩略图
（封面动图/播放量刷新），非结构错误。

### 4.4.1 微信（无 A11Y，只能整屏像素对齐）实测

**小心成功、小心失败——两次结果直接矛盾，第二次是真相。**

第一次（3 帧，慢拖 900ms，步长 376px）看起来很好：

```
w0->w1  dy=+376px  corr=0.9218   次峰 0.7890  锐度 +0.13
w1->w2  dy=+376px  corr=0.9711   次峰 0.7670  锐度 +0.20
```

**周期性梳状峰确实存在**：次峰位置 161 / 376 / 591 / 806 / 1021px，间隔恰好 215px
——就是会话行高。当时判断"真实内容头像昵称把真峰压住，判别安全"。

第二次（8 帧连续序列，快划 300ms，步长 570–1010px）**判据崩塌**：

```
8 帧 7 对：只有 2 对 OK，5 对 AMBIGUOUS
锐度低到 +0.003 / +0.014 / +0.015
次峰仍全部落在 150/365/580/795/1010（215px 梳状）
拼接结果：折叠置顶聊天 / 公众号 / 微信支付 各重复 2–3 次（整屏重复）
```

**栅格形状完全无关**（这是关键排除项）：

| 栅格 | 可拼对数 |
|---|---|
| 12×200 | 2/7 |
| 24×200 / 48×200 / 96×200 | 2/7 |
| 12×400 / 24×400 / 48×400 / 96×400 | 2–3/7 |
| 24×800 / 48×800 | 2/7 |

从 12×200 一路加到 96×800，判别力毫无改善 → **不是分辨率问题，是内容本身的近周期性**。
微信会话行同构（头像左 / 名字 / 摘要 / 日期右），在像素层面构成近似周期信号，
任何 215px 倍数的位移都能拿到相近的 NCC 分数。

**结论（改写位移来源的优先级）**：

```
1. A11Y bbox 差（有树时）          精确，实测 QQ 897px 无歧义
2. OCR 行匹配（无树但有文字）      文本天然去周期——同一句话只出现在一处
3. 像素 NCC                      只在**无文字**场景兜底（视频 / 游戏 / 纯图）
```

**像素 NCC 不能作为主判据**，尤其在列表类界面。此前把它列为第 2 位是错的。

**待验证但尚未测的**：OCR 行匹配在微信上的实际判别力。原理与 A11Y bbox 差相同
（同一文本在两次观察中的 top 差，取众数），且微信每帧本来就在跑 OCR，
数据已经存在——只差一次离线比对。

### 4.4.3 OCR 行匹配实测（微信，无 A11Y）——可用，明显优于像素

数据来源：设备 `memory.db` 的 `lines` 表（pkg=com.tencent.mm），按 `block_id` 取同一段
观察里的多帧（每次滚动捕获 2–5 帧），取 `text + y_top` 做匹配。

**第一版的错误**：直接对 Δy 取整数众数 → 看起来完全不收敛
（票型 `(693,4) (697,2) (695,2)` 被打散成三个值）。原因是 **OCR bbox 本身有 ±3px 抖动**。

**修正后的算法**（三条都是必要的）：

```
1. 排除 Δy≈0 的票：静态元素（状态栏、悬浮通知条、标签栏）会投 0，会把内容位移淹掉
2. 容差聚类（±6px）：把 (693,697,695) 归成同一簇
3. 判据用「最大簇占比」而不是「绝对票数」：占比低说明真的歧义，应当放弃而不是硬猜
```

实测结果（15 组有 ≥3 条内容文本的帧对）：

```
占比 100% 且抖动 ≤10px 的：12/15
占比 75–80%           ：2/15
真歧义（443 vs 506 各 3 票）：1/15
可用率 ≈ 12/15 = 80%
```

对比同场景的像素 NCC：**2/7 = 29%**，且失败时是"近似平局"，无法自我察觉。
文本法失败时会表现为低占比，**可以判断出自己不可靠**——这一点比准确率更重要。

另外：不少帧对显示"全为静态（Δy≈0）"——那是同一次停留内的多帧捕获，本就该判为未滚动。
多帧捕获和位移估计要分开看，不能混。

**结论**：§4.5 的优先级调整成立。微信（以及任何 A11Y 不可读但有文字的界面）
应当走 OCR 行匹配，像素 NCC 仅作无文字场景兜底。

### 4.4.2 新发现的失败模式：视口内的静止浮层会重复

微信顶部有一条**不随列表滚动的悬浮通知条**（位于内容区内，不是工具栏）。
直接按 dy 拼接会让它在长图里重复出现两次（bilibili 测试没遇到，因为其视口内无浮层）。

解法是纯数据的，不需要任何 app 知识——**逐行比较两种假设**：

```
重叠区里，对每一行 y：
  A) 该行是滚动内容 → a[y+dy] 应等于 b[y]
  B) 该行是静止浮层 → a[y]    应等于 b[y]
  哪边差小就属于哪类；B 胜出的行在拼接时跳过（保留第一帧的那份）
```

实测：pair1 判出 122/2150 行静止（5.7%），pair2 判出 73 行（3.4%），
正好对应悬浮条高度。剔除后长图 1200×2902，重复带完全消失，列表无重复无漏行。

**这应当成为拼接算法的标准一步**，而不是针对微信的特解：
"静态层分离 → 全局对齐 → 只贴非静态行"。

注：该结论建立在 dy **正确**的前提下。dy 错误时静态层判定同样不可靠——
所以它依赖 §4.4.1 的位移可靠性，不能单独解决问题。

### 4.5 实测：位移来源（2026-11-21，MIUI V816 / Android 15 / 设备 <device>）

三种候选：一种被证实，一种待验，一种被降级。

| 来源 | 结论 | 证据 |
|---|---|---|
| `AccessibilityNodeInfo.getScrollX/Y()` | **不存在** | `javap android.jar` 无此方法，只有 `isScrollable()` |
| `TYPE_VIEW_SCROLLED` 的 delta | **值错** | bilibili 全 0；QQ `deltaY=3`（实际滚 897px） |
| 同一节点 bbox.top 差 | ✅ **精确** | QQ 18 个共享文本 → 众数 **897px** 出现 11 次 |
| OCR 行匹配 | ✅ **可用**（微信 80%） | 见 §4.4.3；容差聚类后占比 100% 占 12/15 |
| 像素 NCC 整屏对齐 | ⚠️ **降级为兜底** | 微信列表上 5/7 对歧义，见 §4.4.1 |

QQ 实测细节（RecyclerView 134 行，滑动一次）：

```
18 个共享文本的 top 差：897(×11)、0(×6)、-171(×1)
  897  = 真实位移
  0    = 固定 chrome（标签栏、底栏）——众数天然滤掉
  -171 = 重绘异常值 —— 众数天然滤掉
```

**取众数即可**，不需要额外规则剔除静态元素或异常值。这是本设计里少见的"规则自己消失"的地方。

因此采集层的位移来源定为：

```
1. A11Y_BBOX_DIFF：同一节点（按 text 或 resource-id 匹配）前后 bbox.top 差
2. OCR_LINE_DIFF ：同一 OCR 文本行前后 top 差
3. PIXEL_NCC     ：整屏栅格对齐
4. 都不达标 → 显式 NULL（未知）
```

1 和 2 都要**排除 Δy≈0 的静态票 + 容差聚类**（见 §4.4.3）；
三者不设固定优先级，按 §4.8 的融合规则决定谁说话。

前置条件：两次观察要有足够重叠（共享节点/文本 ≥ 3）。无重叠 = 不是"同一段"，不估算位移。

### 4.6 实测：应用分两类，A11Y 有的能读有的完全读不到

| 应用 | A11Y 树 | 可滚容器 | 文本来源 |
|---|---|---|---|
| bilibili | 167 节点 / 38 文本 | ViewPager + GridView | A11Y + OCR |
| QQ | 252 节点 / 38 文本 | RecyclerView (rows=134) | A11Y + OCR |
| **微信** | **1 个空节点 `bounds=[0,0][0,0]`** | **无** | **仅 OCR** |

微信屏幕截图正常（41 条会话可见、文字清晰），但 `uiautomator dump`（独立于本 App 的
第二条 a11y 连接）同样只返回空节点 → **不是我们代码的问题，是微信/系统层面不暴露树**。

**这条直接改写了架构权重**：

- 之前判断："A11Y 差量是免费的 L0 探针，像素只是 WebView/游戏兜底"
- 实际：**微信这种最重要的应用根本没有 A11Y**，OCR + 像素必须是一等公民，不是兜底
- 对微信，文本只能来自 OCR，位移走 OCR 行匹配（§4.4.3，实测 80% 可用）

**关于"错字多"**：用户确认**错字全部来自 QQ**，微信用得少没测过。
所以不能归因于"微信只有 OCR"。真正的问题在 QQ——它有完整的 A11Y 树（38 文本节点），
却仍有错字，说明 `mergeOcr` 的"A11Y 文本优先"在 QQ 上**没有生效**。
这可能是因为 QQ 聊天气泡的内容不在 A11Y 文本节点里（自定义绘制/WebView），
也可能是 bbox 重叠判定失败。**未验证，属于 §13 的待查项。**

### 4.7 实测：主线程成本（已修，2026-11-21）

**成本定位**：给 `PageParser.parse` 加分段计时后，分布是一边倒的：

```
page parse slow 98ms elements=42 stages=[text=0 vis=0 bbox=0 role=1 sig=2 child=94 scroll=0]
page parse slow 99ms elements=42 stages=[text=0 vis=0 bbox=0 role=1 sig=2 child=94 scroll=0]
```

`child`（`getChild` 遍历）占 95%+，其余各项 0–2ms。所以优化点只有一个：**少遍历 / 少解析**。

**反直觉的发现**：同样的树、同样的节点数，耗时差 13 倍：

```
visited=261  →  child=422ms / 519ms / 546ms   （滚动中）
visited=261  →  child=37ms  / 41ms  / 46ms    （静止后）
```

节点数一样，成本差 13 倍 → **成本主要不是算力，是争用**。滚动时目标 App 主线程忙，
每次 `getChild` 的 binder 往返都在等它。**所以正确动作不是少遍历，而是换个时机解析。**

**三条被否掉的路**（都实测过，别再试）：

| 方案 | 结果 |
|---|---|
| 早退（凑够 12 条文本就停） | 无效：文本节点散在整棵树里，visited 几乎不变，仍 223–498ms |
| 换后台线程 | **更糟**：a11y 客户端缓存是线程局部的，换线程后每次 getChild 都走 binder，涨到 1.1–1.9s |
| 截图时再全量补一次 | 更糟：解析次数翻倍，主线程推到 813ms |

**采用的做法**：内容变化路径不在事件里解析，改为「最后一次事件后 250ms 再解析」
（此时画面已稳定，`getChild` 便宜一个数量级）；窗口切换路径仍同步解析（少见，且影响场景边界）。

**结果**：

```
主线程事件处理  修复前 363 / 415 / 581ms  →  修复后 19 / 21 / 26ms   （≈23 倍）
```

**仍然存在的成本**：延迟解析本身还在主线程，App 忙时仍 300–640ms、静止时 40–110ms。
要进一步降，只能减少解析频率（指纹变粗）或找更便宜的树遍历方式（A11Y 未提供）。

**对后续设计的约束**：新设计要加更高频的 L1 探针，**不能复用 `parse()`**——
必须是不递归的零成本探针（只读 `n_nodes` + 文本集合 hash + scrollable 容器列表）。

### 4.8 双判据融合：两个失效域几乎不重叠

这不是"文本为主、像素兜底"的简单优先级，而是两个**互补**的判据。实测证据：

| 场景 | 文本量 | 视觉特征 | 文本判据 | 像素判据 |
|---|---|---|---|---|
| 微信会话列表 | 多（15–30 行/帧） | 行同构、近周期 | ✅ 80% | ❌ 29% |
| bilibili 信息流 | 少（卡片标题） | 封面图各异 | 一般 | ✅ 0.97–1.00，误差 <5px |
| 纯图流 / 视频 / 游戏 | 无 | 图各异 | ❌ 不可用 | ✅ 唯一可用 |

**文本多的地方，像素就不可靠（内容同构）；文本少的地方，像素反而可靠（图像区分度高）。**
这是这批实测里最有用的一条结构性发现——两个判据天然分工，不是备胎关系。

### 4.8.1 融合规则

两个判据各自输出 `(dy, confidence)`，按下面的顺序决策：

```
1. 文本：≥3 行支持、最大簇占比 ≥80%、抖动 ≤12px
   → 采用，置信高
2. 否则 像素：corr ≥0.90、峰锐度 ≥0.05
   → 采用，置信中
3. 两者都过阈且 |dy_text − dy_pixel| ≤ 12px
   → 采用像素值做细校准（文本给粗定位，像素给精确值），置信高
   → 文本定序、像素定位：这正好是两者该干的活
4. 两者都过阈但互相矛盾（差 > 一行高）
   → **不拼**，标 NUM_OVERLAP，保留两帧各自为独立块
   （宁可断开，不要拼错——断开只是多一段，拼错是结构错误）
5. 都不过阈 → 判 NO_MOTION / UNKNOWN，显式未知
```

**规则 4 是重点**：不允许"谁领先就用谁"。两个独立判据在都自信的情况下互相矛盾，
说明数据本身有歧义，硬选一个就是在制造错误断言。

### 4.8.2 无文字持续下滑

连续下滑且界面无文字（纯图流）时：

- 文本判据全程沉默（正常，不是失败）
- 像素判据承担全部工作，但每对都要过 `corr` 与峰锐度双阈
- 累计误差会随帧数累积（每对 ±5px，10 帧后可能 ±50px）
  → **每 N 对做一次闭环校验**：用第 1 帧与第 N 帧直接对齐，与逐步累加的值比对；
    偏差超阈值则重新分段（把这段切成两段更短的链，各自独立定位）
- 若有任何一帧出现少量文字（如列表里的一个标题），优先用它做锚点纠偏

即：**不是"没有文字就全靠像素"，而是"文字出现的那一刻立刻用它纠偏"。**

### 4.9 明确不做

- 不做"屏幕变暗 → 新起点"：变暗可能是抽屉、息屏、亮度自适应、夜间模式、控制中心。
  把变暗当边界会在抽屉关闭后**丢失返回路径**。
- 不做上下文状态机推测 UI 树。UI 导航是树，但采集层不需要树——只需要留下能推出树的证据
  （window_stack 有序 + parent_idx + 输入事实）。

## 5. 去重

**去重针对"相同"，不针对"相关"。**

```
content_hash = H( pkg + activity + window_stack 顺序 + 规范化 text 集合 + grid )
```

- 相同 → 只存一份 observation，但**保留时间事实**：`t_first / t_last / seen_count`。
  （"同一画面停留了 40 秒"是真事实，与"这是同一条消息"是判断，两者不可混。）
- 相关（属不属于同一上下文 / 同一群）→ **不判断**，留给重建。

去重前移的收益是**一次性**的；把去重留在查询期的成本是**每问一次付一次**。

## 6. 三层模型：内容 / 访问 / 视图

这一节是整个设计里**最容易搞错的一层**，搞错了会产生"一天去了两次被合并成一次"这类
不可接受的内存错误。

```
block   内容寻址      "这一段画面/文字是什么"       去重：相同内容只存一份
visit   时间寻址      "我什么时候在哪看了多久"      不去重：一条一个，永不合并
view    按问题生成    "长截图 / 某段叙述"           不落盘，可重算
```

**去重只发生在 block 层，visit 层永不合并。**

### 6.1 为什么必须分开

典型场景：一天里两次打开同一个群。

```
10:00 进群，看了 A..F 六条消息，退出
15:00 再进群，A..F 还在，新增 G..K 五条

错误做法（把 visit 也去重）：
  只有一条链 → 记忆里"只去过一次" → 问"我今天去了几次"必错

正确做法：
  block_A..F   存一份（15:00 那次哈希相同，命中已有 block）
  block_G..K   新存
  visit#1 = (10:00, [A..F])
  visit#2 = (15:00, [A..F, G..K])      ← 两条访问记录，各自的引用表
```

- 问"今天我去了几次这个群" → 两条 visit → **正确**
- 问"G 这条是谁说的" → visit#2 → block_G → **同一份内容，不重复存**
- 问"这个群聊了什么" → 任一 visit 展开 → 内容相同，答案一致

**长截图不是存储单元，是 visit + block 的渲染结果。** 同一批 block 可以在两条
visit 里被渲染成两条不同长度的长截图，也可以被同一条 visit 在查询时渲染成不同粒度。
这与公理 A3（重建是视图）一致，只是把"段"换成了"长截图"。

### 6.2 block 与 visit 的字段

```
block
  block_key      内容哈希（文本集合 + 栅格 + pkg），主键
  text_lines     [(text, bbox, line_no)]   去重后的正文
  grid           12×200 luma
  shot_ref       证据图引用（可为 NULL）
  first_seen     首次出现时间（仅作参考，不代表"看过"）

visit
  id, t_start, t_end
  pkg, activity, window_sig
  segments       [(block_key, align{dy}, t_in, t_out)]   有序
```

**visit 不含 `object_key`。** "这属于哪个群"是判断，放在重建层；
visit 只用事实（时间、pkg、窗口签名）定位"我看了哪块屏幕"。

### 6.3 访问边界怎么定（判断，但可撤销）

visit 的切分是重建层的判断，依据全是可测事实：

```
超时：距上次观察 > N 分钟      → 新 visit
离开：pkg 变化 / 屏幕熄灭      → 结束当前 visit
回归：回到同一 pkg + 同签名    → 新 visit（不是续上一个）
```

切错了只影响一次视图，且可重算——因为 block 层不受影响。
**这正是把访问与内容分开的收益：访问层的错误不会污染内容层。**

### 6.4 重建层契约

```
reconstruct(range, intent) → View

intent（至少覆盖现有三种视图）：
  notice   "我有没有刷到过 X"    按屏幕状态对齐
  thread   "这个群里聊了什么"    按内容连续性对齐
  session  "下午我在干嘛"        按窗口/任务序列对齐

View  = [Group]
Group = { observations[], align{dx,dy}, coverage{covered_ms, gaps[]}, evidence[] }
```

**约束**：
- View **不得落盘为事实**。可缓存，缓存必须带 `derivation_version`，版本变化即失效重算。
- 同一段观察，不同 intent 必须能生成不同 View，且互不污染。
- View 必须能输出**覆盖率声明**（本视图覆盖了什么、空档在哪、为什么空）——
  这是现有 `recall` 已建立的契约，保留。

**上下文的边界判据属于重建层**，可用几何量（位移方向 d、内容驻留率 r）作为**证据**，
但不得作为采集层的固化标签。判错只影响这一次 View，重算即可。

## 7. 提交与携带（解决"观察日志是设备本地的，但记忆要跟人走"）

沿用既定的两库分离：

```
观察日志   = 证据层：设备本地，可 GC，不随设备迁移
commit     = 记忆层：提炼产物，随设备迁移，一旦提交即冻结为 canon
```

```
commit(day) → 记忆事实（lines 粒度 / 分组 / 事件 / 日叙事）+ commit_marker
```

- **提交前**：同一天内可反复重建、换算法、对比效果——这是优化窗口。
- **提交后**：冻结，不再重算。观察日志随后可被 GC。
- 换设备后：旧记忆在（冻结的 canon），旧观察没了（不可溯源），新观察在新设备继续长。

这与既定目标一致：**"换设备后 agent 和用户的记忆还在，但原始数据不可溯源，旧回忆还在，新的能继续长。"**

关键区别：现在这是**偶然发生**（重建库时把数据挤掉了），以后是**显式的 commit 边界**。

## 8. 可测性（哪些是真的能测，哪些不能）

| 指标 | 可测 | 测法 |
|---|---|---|
| 漏采率 | ✅ | 回放相邻 observation；grid 差大且中间无帧 = 一次漏采 |
| 拼接可用率 | ✅ | 相邻 observation 对齐相关度低于阈值 = 硬失败 |
| 去重率 | ✅ | observation 数 / 原始触发数 |
| 单帧解析成本 | ✅ | `elapsed_ms` 直方图（已有） |
| 存储/天 | ✅ | 直接量 |
| **分段正确率** | ❌ | 无真值 |
| **帧级归属** | ❌ | 无真值 |

**诚实结论**：这一整套换来的不是"正确性可测"，而是把「不可测 + 不可逆」换成
「不可测 + 可逆」。**可逆是唯一硬的收益**，不要让话术把它说成可测。

规则预算因此全部投给**覆盖率**（可测）和**去重**（可测），不投给分类（不可测）。

## 9. 迁移路径（只增不减，可随时停）

```
阶段 1  加 observation 三表 + 字典表；采集双写。
        object_key/page_title/kind/side 停止写入（字段保留，不回滚旧数据）
```

### 11.1 测试数据生成约束（踩过的坑）

1. **列表滚到底会让位移测量失真**：到底后继续滑，画面不移动，会被判成
   `NO_MOTION` / 小位移，**`漏采率` 和 `拼接可用率` 都会被算错**。
   采数据前必须确认不在列表末端。
2. **微信从列表顶部下滑会拉出"小程序面板"**（不是回滚，是系统手势）。
   该面板本身不滚动，导致整段序列 `dy=0 corr≈0.999`，看起来像"对齐算法正常但画面没动"。
   实际是采错了界面。判断方法：看截图，不要只看日志。
3. **快划（300ms）会让列表行 recycle/rebind**，重叠区内容不再逐像素相同，
   NCC 显著退化；慢拖（900ms）时明显更干净。**采样时的手势速度会影响数据质量**，
   这本身就是一条"采集条件"而不是"算法条件"。

## 12. 顺带发现的既有缺陷（已修）
**假 STALLED 报警**：心跳打出

```
trace: event stream STALLED lastEventAgoMs=1794904060624 hostService=running
  a11y=system-enabled screenOn=true（MIUI bound-but-deaf；需要用户重新开关无障碍）
```

`1794904060624` 就是 `System.currentTimeMillis()` 本身。根因是**时钟混用**：
`TraceAccessibilityService` 里两处 `onSkippedHeartbeat(nowEv, ...)` 传的是
`SystemClock.uptimeMillis()`（开机毫秒，量级 1e6），而 `TraceModule.lastEventAgoMs()`
用 `System.currentTimeMillis()`（epoch 毫秒，量级 1.8e12）去减 —— 差值恒 ≈ epoch。

此时 a11y 实际完全正常：事件在流、截图在出、`event#350` 照打。
它把"正常"报成"MIUI bound-but-deaf，需要重新开关无障碍"，**会让人去修一个不存在的问题**。

修法（已应用）：两处改传 `System.currentTimeMillis()`，与其他调用点一致。

## 13. 待开专题：降低 OCR 误读

你反馈"一打开会话就发现错字多"。这与本设计同源——**采集层采到的东西干净与否**
直接决定上层一切。

**已修正的错误归因（留档，避免再犯）**：我最初推断"错字来自微信，
因为微信 A11Y 树为空、文本 100% 来自 OCR"。用户确认**错字全部来自 QQ**，
微信用得少、没测过。所以这个因果关系是错的，撤回。

**真正值得追的线索**：QQ 有完整的 A11Y 树（252 节点 / 38 文本节点），
却仍然出现错字 → `mergeOcr` 的"A11Y 文本优先"在 QQ 上没生效。候选原因：

1. QQ 聊天气泡的内容不在 A11Y 文本节点里（自定义绘制 / 内嵌 WebView）
2. `mergeOcr` 的 bbox 重叠 >60% 判定失败（OCR 框与 A11Y 框错位）
3. 文本长度差 2 倍的保护规则把它挡掉了（`lo * 2 < hi` 那条）
4. 落库时 A11Y 文本与 OCR 文本被覆盖的顺序问题

**验证方法**：取一条已知有错字的 QQ 会话 trace，把它的 `elements`
（含 source=A11Y/BOTH/OCR 标记）和 OCR 原始行按 bbox 摆出来对照，
一眼就能看出是"A11Y 压根没有这段"还是"A11Y 有但没被采用"。
这两者的修法完全不同，**不要先猜**。

已核实的现状（避免重复排查）：

- OCR 输入**已经是全分辨率位图**：`saveAndOcr(bmp)` 用 `InputImage.fromBitmap(bmp, 0)`，
  bmp 是 `takeScreenshot` 原始帧，未缩放。所以"先高清 OCR 再降分辨率留底"
  这半句**已经是现状**，瓶颈不在分辨率。
- 落盘证据图是同尺寸位图，JPEG quality 70（`saveShotFile`）。
- `mergeOcr`：OCR 框与 A11Y 框重叠 >60% 时用 A11Y 文本。对 A11Y 可读的应用有效，
  对**微信完全无效**。

待测（下一步，不改采集逻辑即可做）：

1. 取同一帧的 `ELEMENTS`（A11Y 文本+bbox）与 `traces.text`（OCR），按 bbox 对齐逐条比对。
   分三类：A11Y 有 OCR 无 / 两边一致 / 两边不一致。**第三类才是误读的真实量级**，
   现在这个数完全没有。注意：这只能量 A11Y 可读的应用（bilibili/QQ），**微信量不了**。
2. 微信的误读只能用"同一文本在不同帧的 OCR 结果是否一致"来间接估——
   稳定读错（每帧都错成同一个字）无法用一致性检出，仍需人工抽样。
3. 备选方向（不预设结论）：分块 OCR / 逐行 OCR / 提高 element 粒度 /
   两遍不同预处理取一致性最高者 / 对微信这类无 A11Y 应用引入第二 OCR 引擎做交叉校验。
