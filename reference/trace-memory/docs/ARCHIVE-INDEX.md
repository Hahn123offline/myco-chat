## 五、反复翻案的七个话题（**这一节最值钱**）

如果只读一节，读这一节。每一条都是"试过 N 次才定下来"，重走一遍成本很高。

**① 要不要安卓 App** —— 曾判断"PC adb 轮询就够、砍掉安卓开发"（11-15）→ 当天推翻，改成真机 App。

**② 采集主通道** —— 曾定"ADB 为主、不走 root"（11-15）→ 实际实现是纯无障碍；同一篇文档 §16 自己就修正了。

**③ 要不要碰云** —— 曾明确"不碰云端"（11-15）→ 次日云打标 20 条成功；再后来直接引入云 API 强模型。

**④ 检索方案换了三代** —— 向量（11-15，未走）→ LIKE + FTS5 讨论（11-16）→ BM25 + tieBreak + anchor（11-18，定格）。

**⑤ 出网矩阵改了三次** —— 四档 WHITE/GRAY/BLACK/UNKNOWN（11-16 14:00）→ 取消三档只剩 BLOCK/MASK（11-16 17:31）→ 又改回三级 NEVER_CLOUD/REDACT_THEN_CLOUD/NORMAL（11-17）。
连带翻案：微信/QQ 能否上云（前：黑白名单永不出；后：掩码后上云）。

**⑥ 人名/地址要不要脱敏，翻了四次** —— 350M NER + 角色化 + 模板化（11-15）→ 1B 补人名地址（11-16 13:15）→ 不再做人名/地址/机构名脱敏（11-16 17:31）→ 1B 输出含 name，人名掩码又回来（11-17）。

**⑦ 端侧模型能干什么** —— 35B 约 10 tok/s"夜间合并绰绰有余"（11-15）→ 实测 4–8 tok/s 天花板、35B 不上机（11-16）→ 1B 会编造、不能实时打标（11-16）→ 只用专门 350M PII 编码器（11-16）→ NER 也被判"性价比不成立"（11-16）→ 又让 1B 做逐元素敏感判定（11-17，换了任务）。

### 五个仍然成立的判断（从翻案里沉淀出来的）

```
1. 安全默认是"降级到还能做的最大能力"，不是"什么都不做"；降级要有可解释的损失
2. 指标变差时先验量具 —— 探针错三次，一半"退化"是假的
3. 不让模型做"判断"，让它做"产出"（"用片段回答、答不了就 null" → 负例 0）
4. 两库按语义分而非体积分：记忆库可携带、证据库可弃；记忆库不能依赖证据库才能用
5. 缺口三态语义不同（recording_off / app_only / no_record），>20 分钟才算缺口
```

## 六、已知文档缺陷（读的时候别被坑）

```

召回与日叙事（11-18）        L0 时间窗分片 / L1 子链 / L2 事件 body / L3 日叙事
记忆合并-父子链（11-18）     把"L0 chunk ≤45 分钟"当时间窗，§5 又用"块→链→事件→线程"四个名字
```
